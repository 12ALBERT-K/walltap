## LATEST SESSION (2026-10-11) — "users can't get in / process dies"

Investigated live. Root causes found and FIXED + VERIFIED in code
(commits d5f2520 and 8fd9c4c — still need the deploy above to go live):

  1. LEGACY LOGIN TRAP — accounts created before the username system keep REAL
     emails (admin1 = wacudigitalhub@gmail.com, calltest = HSX_...). The old
     client mapped any typed username to <name>@walltap.local, so signing in by
     username alone failed FOREVER with "Wrong username or password" even with
     the right password. NEW: POST /api/resolve-login maps profiles.username →
     stored email (via admin_profiles view); the browser retries once with the
     real email before showing the error. Verified in real Chrome: legacy
     account signs in by username only; fresh signup + cross-device sign-in
     still work; wrong passwords still show the same generic message.
  2. PROCESS CRASH VECTOR — server had async handlers (requireAuth, DELETE
     /api/posts/:id, and the GET/POST/refresh routes) that Express 4 does not
     wrap: a rejected promise became an unhandledRejection and Node killed the
     whole process (a flaky Supabase response while spinning up = dead site).
     NEW: asyncHandler() wrapper on every async route + process-level
     unhandledRejection/uncaughtException handlers that log and stay up.
  3. COLD START (not a code bug) — Render free tier still 503s for ~30-60s
     after ~15 min idle. Seen live again today. Cheap mitigation: a cron
     (cron-job.org) hitting https://walltap.onrender.com/config.js every ~10
     min keeps the instance awake.

  Verified this session: all 44 local e2e tests pass on the patched server;
  preflight passes; committed the fix; full Chrome UI verification passed
  15/15 (legacy username sign-in, new signup, same-device re-login, fresh
  "another device" profile, wrong-password rejection); pinned Node engine to
  ">=20 <26" (commit 8fd9c4c) after the new deploy tried Node 26.

## 5. WHAT WAS FIXED TODAY (all committed + live)

The big one: the app looked deployed but every API call 503'd.

  * DATABASE_URL used Supabase's DIRECT host (db.<ref>.supabase.co), which is
    IPv6-ONLY (AAAA record, no A record). Render free tier has no IPv6 egress →
    ENETUNREACH → initSchema() failed → ready=false → every route 503'd while
    / and /config.js still returned 200, so it LOOKED deployed.
    Fix: use the IPv4 pooler. → commit 27120be
  * sslmode=require breaks node-postgres against Supabase (self-signed cert).
    Only sslmode=no-verify works. → .env
      Verified by direct test against db.hbcsujvcizcnpgxkcxuu.supabase.co:5432
      using the repo's own `pg`:
        sslmode=require  -> FAIL: self-signed certificate in certificate chain
        sslmode=prefer   -> FAIL: same
        sslmode=verify-ca-> FAIL: same
        sslmode=no-verify-> OK
      Do not "correct" this back to `require` — it is what the pg driver treats
      as an alias for verify-full. server.js:256 only passes its own
      `ssl:{rejectUnauthorized:false}` when the URL has NO sslmode= at all, so
      whatever you put here is what pg uses. no-verify and omitting sslmode are
      equivalent; no-verify is the explicit, self-documenting choice.
  * public/app.js declared top-level `const supabase`; the Supabase CDN bundle
    declares `var supabase` globally. Two classic <script> tags → SyntaxError at
    PARSE time → entire file dead, zero listeners, login button inert.
    Fix: wrapped app.js in an IIFE (2 lines, no rename).
    → commit 37b69d8
  * provision-admin left a half-created confirmed account when its grant failed,
    dead-ending the retry. Now reuses the trigger's username + rolls back.
    → commit acbd7a5
  * server.js now binds the port BEFORE DB init, so slow init can't fail a
    deploy health check. → commit aed5e86
  * preflight.js now FAILS on an IPv6-only DATABASE_URL host, so the 503-only
    deployment can't silently come back.
